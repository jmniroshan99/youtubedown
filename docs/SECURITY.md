# Security design and operating notes

- Treat submitted URLs, titles, metadata and extractor output as untrusted. React renders strings as text; no source HTML is injected.
- The API validates schemes, credentials, ports and DNS answers. The egress proxy independently validates every outgoing connection and connects to a numeric public address, closing the re-resolution/DNS-rebinding gap. It refuses mixed public/private DNS answers, IPv4-mapped local IPv6 and IPv6 transition addresses.
- API, worker, Redis and scheduler use an `internal: true` Docker network. Processing services reach public destinations only through the forward proxy, which has no public published port. The production TLS gateway separately has outbound access and its own internal network. Do not remove this boundary, add host networking, mount Docker's socket, or attach the worker directly to a public network.
- Media subprocesses receive a minimal environment, not parent service keys. Temporary request files may contain source URLs and are removed. Containers run without capabilities, with a read-only root and explicit CPU/memory/process limits.
- Fixed program arguments and server-held format selections are used. Users cannot supply shell flags, executable plugins, output paths or custom executable adapters.
- Auth uses the Supabase Auth server, not unverified decoded claims. Verified anonymous Auth users are allowed for normal operations. Administrators must be non-anonymous and have fresh server-managed `app_metadata`; editable `user_metadata` is ignored.
- Every temporary job/file mutation has a verified ownership check. The API enforces the owner in Redis job state; unpredictable IDs alone are insufficient. Existing Supabase tables retain RLS and explicit grants, and browser roles cannot administer providers. Legacy job tables/RPCs are preserved but new downloads do not write to them.
- Job reservation, idempotency and per-user active/daily quotas use atomic Redis operations shared by API instances. Expiring usage counters are independent from deleting a current job. No new download-history rows or permanent quota ledger entries are created in Postgres.
- Storage is private, with no client upload/sign/read policies added. API-issued links are bearer capabilities and should not be shared unintentionally. Existing project-wide Storage policies must be reviewed before applying this app to a previously configured project.
- Thumbnails use an authenticated, bounded server fetch, MIME allowlist and protected egress, preventing client-side access to an untrusted metadata URL. SVG thumbnails are not served.
- Raw extraction errors, source URLs and tokens are not logged by the media engine. API access logs are disabled. Avoid adding verbose HTTP debugging in production.
- The proxy is deliberately small and does not implement a general browser proxy or authentication. Its security assumes it is only reachable from the private Docker network. Add an infrastructure firewall and monitor resource use in production.
- Egress controls do not replace keeping FFmpeg, Node, Python, yt-dlp and dependencies patched. Resource limits contain some failures but this is not a formal security audit.
- See VERIFICATION.md for checks actually performed against this release. Run live identity, Storage, network-isolation, browser-download and cleanup acceptance checks against the final deployment.

## Guest boundaries

- Anonymous visitors get independent Supabase authenticated identities, not a shared account. All existing owner RLS policies still apply. The frontend clears private query/mutation state and aborts requests when identities change; account switching also resets route-local state.
- Guest limits are selected from the server-verified user, never a request body or browser claim. A private format-policy snapshot survives retries and queue recovery. Current stricter limits win. The worker applies size/duration bounds during extraction and verifies final output before upload. Guest media with unverified duration is rejected.
- Redis atomic operations keep per-identity active/daily reservation and idempotency consistent. Redis Lua checks and increments all guest rate budgets across API instances. Shared network budgets prevent a new guest identity from resetting every allowance. The supplied Redis service disables AOF/snapshot writes. Restarting Redis loses current jobs/queue/limiter state, and rotation of its HMAC key also resets network counters. Existing volume identifiers and older files/backups are not scrubbed. Use external/global resource controls as well as application limits.
- Rate keys contain HMAC hashes of IPv4 addresses or IPv6 /64 prefixes, not raw IPs. Retention is bounded by the current minute/day window. NAT users share a budget; different networks can still have separate allowances. Rate limits are not a complete anti-bot system. Enable supported CAPTCHA and appropriate anonymous-signup rate limits in Supabase before public exposure.
- Incoming X-Forwarded-For is ignored unless the actual TCP peer matches explicit TRUSTED_PROXY_CIDRS. The production Caddy override uses a dedicated /32 address and replaces incoming forwarding headers. Uvicorn proxy-header interpretation is disabled so it cannot silently overwrite the peer. Never use 0.0.0.0/0, ::/0 or a wildcard trust rule. Review any additional load balancer/CDN chain before changing trust.
- Every API response is private/no-store, including signed URLs and errors. The frontend requests private APIs with no-store. Large files still go directly from private Storage via short-lived signed URLs.
- Cleanup removes expired completed files and unreferenced failed/cancelled media after worker locks clear. Issuing a signed link extends an opaque deletion lease by the configured transfer grace. Source URLs/titles are not kept in that cleanup ledger. An independent bounded Storage sweep removes expired objects in the dedicated temporary namespace even after Redis state loss. It does not delete accounts, active jobs or legacy history. Do not run broad anonymous-account deletion SQL as a cleanup shortcut. Optional account merging/upgrading is not part of this release.

## Local ingress in 1.2.2

The API no longer publishes its own host port. The local override connects the API to a second internal network (`local_api`). A separate Caddy gateway connects to that network and a normal bridge (`local_ingress`) and publishes only `127.0.0.1:8000`. Its upstream is fixed to `api:8000`; it is not a general forward proxy. The gateway has no Redis/private-worker network membership, server keys, Docker socket, writable root filesystem or administration endpoint. The API and workers receive no direct outbound network. The existing guarded forward proxy remains their outbound path.

This local gateway is excluded from production because it is defined only in the local override. The production HTTPS gateway, exact origin checks and trusted-proxy configuration are unchanged. Local guest network limits conservatively share the gateway's observed network identity; do not widen trusted-proxy ranges just to recover host connectivity.

### Caddy capability compatibility in 1.2.3

The official Caddy image marks `/usr/bin/caddy` with `cap_net_bind_service=+ep`. Linux may reject execution if that capability is absent from the container's bounding set, even though this gateway listens on unprivileged port 8080. The local service therefore drops ALL and adds only NET_BIND_SERVICE. This permits binding privileged ports inside the container; it does not grant network administration, raw sockets, host networking, root identity or access to processing-service secrets. Only localhost port 8000 remains published. The non-root UID, read-only root, no-new-privileges, resource limits and network separation remain in force.

Startup validates the executable and mounted Caddyfile in a temporary container using the same service settings. The diagnostic reads only selected Docker state fields and, for a stopped/restarting gateway, up to 30 recent gateway log lines. It returns fixed error categories and excludes raw evidence, environment values and healthcheck logs from its output and diagnostics.txt.

## Destination DNS in 1.2.4

Media URL prechecks in API/workers validate syntax and public literal addresses without external DNS, because those containers have no outbound network. They are not a complete SSRF decision by themselves: all media I/O must use the guarded egress proxy. The proxy resolves every target, rejects the connection if any DNS answer is non-public, and opens the socket to a validated numeric address without a second lookup. Redirects and additional media hosts undergo the same gate. Missing worker/thumbnail proxy configuration fails closed.

The shared strict validate_url default still resolves/checks DNS for callers at the egress boundary. Thumbnail requests use an explicit proxy with trust_env=False so NO_PROXY cannot bypass the boundary. DNS failure and target rejection have distinct fixed proxy responses; no raw exception, URL or header is returned. A proxy does not inject another HTTP response after a tunnel or upstream response has started.

The worker egress diagnostic uses two fixed CONNECT targets and never downloads video data, prints DNS answers, accepts user URLs or exposes a resolver endpoint. The local CORS override lists only localhost:5173 and 127.0.0.1:5173; production origins remain separately configured.
